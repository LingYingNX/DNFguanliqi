## 项目诞生

### 最初问题

最早的归档资料（2026-07-02 至 2026-07-07）记录了项目的原始动机：DNF NPK 文件长期散落，分类、预览、启用、停用和恢复都不方便。产品从一开始就被定义为本地文件工作台，而不是补丁平台。

最初确定的产品原则是：

1. 只管理用户已有文件。
2. 用户看到的分类和组必须对应真实目录和真实文件。
3. 便携运行，更新时可以替换程序而保留用户数据。
4. 可预期、可撤销、可验证优先于装饰性功能。

### 初代实现

初代资料显示，早期版本使用 Electron、Node.js、原生 HTML/CSS/JavaScript，界面版本为 1.1，目标是 Windows x64 portable。初代源码结构和远端信息已经过时，只保留在 `docs/archive/legacy-knowledge/` 作为历史证据。

归档没有记录最初编码的精确日期，因此应区分两个时间点：初代产品需求来自 2026-07 初的历史资料；当前可以重新安装、构建、测试和启动的源码基线从 2026-07-18 的 clean rewrite 开始。

## 当前架构记忆

```text
Electron main
  -> core filesystem/state/application services
  -> typed IPC handlers
  -> preload validation and named API
  -> React renderer/workspace/components/styles
```

- `src/main` 负责窗口、应用路径、IPC 注册、系统文件选择和受管图片协议。
- `src/core` 负责真实文件、路径安全、状态、事务、分类、组、导入、移动、安装、回收、预览、壁纸和外观。
- `src/shared` 负责 Zod 输入约束、DTO、IPC 契约、结果类型和恢复契约。
- `src/preload` 只暴露命名 API，不暴露 `ipcRenderer`、Node `fs` 或通用 invoke。
- `src/renderer` 负责选择、筛选、视图、对话框、命令状态和样式，不直接读写磁盘。
- `tests/integration` 验证真实临时目录和事务不变量；`tests/e2e` 验证真实 Electron 窗口和用户工作流。

## 不可随意改变的领域决策

- 分类就是 `patch-categories` 下的真实文件夹。
- 组就是带 `.dnf-group.json` 的真实文件夹，不是虚拟标签；组启用等同于安装组内所有 NPK。
- 父分类默认只显示本层项目，递归查看必须显式开启。
- 移动、重命名、分组、回收、恢复和启停必须先预检，再执行文件事务，失败时逆序补偿。
- 停用只删除仍与安装记录哈希一致的目标文件，禁止覆盖用户后来修改过的文件。
- 预览图通过双击预览区域设置，右键菜单不再提供同名入口。
- portable 版数据放在 EXE 同级的 `data` 和 `patch-categories`，升级不得覆盖用户数据。
- 损坏状态不能静默当成空状态；应用进入只读恢复模式并保留问题文件路径。
- 用户 NPK、壁纸、`data`、构建输出、截图和运行时目录不进入源码提交，也不进入 Markdown-only 知识库。

## 长期迭代方法

### 开始一个迭代

1. 先读本文件、`docs/FUNCTION_MODULES.md`、`docs/MAINTENANCE.md` 和对应 `.learnings/` 条目。
2. 把新想法写入 `.learnings/功能需求.md`，先判断是否仍属于本地文件工作台。
3. 明确真实文件结果、状态 JSON、界面状态和错误行为四类成功标准。
4. 先补会因缺失行为失败的测试，再写最小实现。

### 完成一个迭代

1. 按风险执行 lint、typecheck、集成测试、E2E、build、portable 和 packaged 门禁。
2. UI 改动保存截图或真实 Electron 自动化证据；文件操作保存目录和 JSON 结果。
3. 错误写入 `.learnings/错误记录.md`，非显然经验写入 `.learnings/学习记录.md`。
4. 更新 `docs/PROJECT_HISTORY.md`、`docs/PROJECT_MEMORY.md` 或 `docs/FUNCTION_MODULES.md`，避免把新事实只留在聊天里。
5. 只复制固定五文件到知识库，复核目标没有额外目录、`.git`、源码、依赖或构建产物。
